 
# OWASP Security Shepherd [![OWASP Flagship](https://img.shields.io/badge/owasp-flagship%20project-48A646.svg)](https://www.owasp.org/index.php/OWASP_Project_Inventory#tab=Flagship_Projects) 
The [OWASP Security Shepherd Project](http://bit.ly/owaspSecurityShepherd) is a web and mobile application security training platform. Security Shepherd has been designed to foster and improve security awareness among a varied skill-set demographic. The aim of this project is to take AppSec novices or experienced engineers and sharpen their penetration testing skill set to security expert status.

# Where can I download Security Shepherd?

### Virtual Machine or Manual Setup
You can download Security Shepherd VM's or Manual Installation Packs from [GitHub](https://github.com/OWASP/SecurityShepherd/releases)

### Docker (Ubuntu Linux Host)

> [!WARNING]
> **The Docker Compose setup is a quick start, not a production deployment.** It is meant for trying Security Shepherd out, development, and classroom labs on a network you control. Security Shepherd is deliberately vulnerable, so never expose it to the internet.

The quick start uses these defaults:
* Login `admin` / `password` for the platform. You are asked to change it after the first login.
* A self-signed TLS certificate, generated by `mvn -Pdocker` with the keystore password from `.env`. Browsers warn about it. Anyone who has an image you built, or a prebuilt image you pulled, has that certificate's private key.
* The MariaDB root password from `.env` (`CowSaysMoo`), which is also built into the Tomcat image.
* MongoDB runs without authentication. MariaDB and MongoDB are published on `127.0.0.1` only.

If you run it for anything more than that, at least:
* change `DB_PASS` and `TLS_KEYSTORE_PASS` in `.env` before building;
* use your own TLS certificate: after the Maven build, replace `target/docker/tomcat/<TLS_KEYSTORE_FILE>` with your own PKCS12 keystore and set `TLS_KEYSTORE_FILE`, `TLS_KEYSTORE_PASS` and `ALIAS` in `.env` to match before `docker-compose up --build`. Or run Shepherd behind a reverse proxy that terminates TLS;
* keep it on an isolated network, and only enable the unsafe levels (XXE) when you need them.

#### Initial Setup
```console
# Install pre-reqs
sudo apt install git maven docker docker-compose openjdk-17-jdk

# Clone the github repository
git clone https://github.com/OWASP/SecurityShepherd.git

# Change directory into the local copy of the repository
cd SecurityShepherd

# Adds current user to the docker group (don't have to run docker with sudo)
sudo gpasswd -a $USER docker

# Run maven to generate the WAR and the database scripts. The HTTPS certificate is generated
# when the web container first starts.
mvn -Pdocker clean install -DskipTests

# Build the docker images, docker network and bring up the environment
docker-compose up
```

Open up an Internet Browser & type in the address bar;

* [localhost](http://localhost)

To login use the following credentials (you will be asked to update after login);

* username: ```admin```
* password: ```password```

Note: Environment variables can be configured in dotenv ```.env``` file in the root dir.

#### HTTPS certificate
The image contains no TLS certificate or private key. On its first start, the container generates a self-signed certificate for `localhost` and keeps it in the `conf` volume, so every installation gets its own key, and it survives restarts and rebuilds. Your browser will warn about it, because it's self-signed.

The keystore's file name, password and alias come from `TLS_KEYSTORE_FILE`, `TLS_KEYSTORE_PASS` and `ALIAS` in `.env`, and the certificate's subject from `DNAME`. Without `TLS_KEYSTORE_PASS`, a random password is generated and kept next to the keystore in `conf/.tls-keystore-pass`.

To use your own certificate, copy a PKCS12 keystore into the `conf` volume under the name in `TLS_KEYSTORE_FILE`, set `TLS_KEYSTORE_PASS` and `ALIAS` in `.env` to match it, and recreate the container so it picks up the new `.env`:

```console
# Written by the container's tomcat user, so Tomcat can read it
docker exec -i secshep_tomcat sh -c 'cat > /usr/local/tomcat/conf/shepherdKeystore.p12' < my-keystore.p12
docker-compose up -d web
```

To get a new self-signed certificate, delete the keystore (and `conf/.tls-keystore-pass`, if there is one) and restart:

```console
docker exec secshep_tomcat rm -f /usr/local/tomcat/conf/shepherdKeystore.p12 /usr/local/tomcat/conf/.tls-keystore-pass
docker-compose restart web
```

Do this once if you ran an `owasp/security-shepherd:dev` or `4.0.0-SNAPSHOT` image published on 25 October 2026. Those still shipped a keystore, the same one in every copy of the image, so anyone who pulled them has its private key. Images you built yourself had a key generated on your machine and aren't affected.

Pre-built images are published to Docker Hub as [`owasp/security-shepherd`](https://hub.docker.com/r/owasp/security-shepherd). [Checking the Docker images](docs/verifying-images.md) explains the tags and how to check an image's SBOM and provenance.

#### Building an up-to-date image
When the Tomcat image is built, it installs the Ubuntu security updates released since its base image was published. Docker caches the base image and that build step, so rebuilding with `docker-compose up --build` can reuse an old base image and old packages. To build an image with the latest updates, rebuild it without the cache and recreate the container:

```console
mvn -Pdocker clean install -DskipTests
docker-compose build --pull --no-cache web
docker-compose up -d
```

#### Upgrading an existing Docker environment
Security Shepherd now runs on Tomcat 11. Tomcat's `conf` directory lives in the `conf` Docker volume, and Docker only copies the image's files into a volume when the volume is first created. An existing environment would therefore start Tomcat 11 with its old Tomcat 9/10.1 `server.xml` and `web.xml`. That volume has to be recreated. Database data is in the separate `data` and `mongodata` volumes, so it is kept.

The `conf` volume also holds the TLS keystore and the `database.properties` / `mongo.properties` connection settings, so **back it up first**:

```console
docker-compose down
# The volume is named <project>_conf; check with: docker volume ls
# The archive holds the TLS private key and database password. Keep it outside the repository
# (the repository root is the Docker build context) and readable by you only
BACKUP_DIR="$HOME/shepherd-conf-backup"
mkdir -p "$BACKUP_DIR" && chmod 700 "$BACKUP_DIR"
docker run --rm -v securityshepherd_conf:/conf -v "$BACKUP_DIR":/backup alpine sh -c \
  'umask 077 && touch /backup/shepherd-conf-backup.tgz && chmod 600 /backup/shepherd-conf-backup.tgz \
   && tar czf /backup/shepherd-conf-backup.tgz -C /conf .'
docker volume rm securityshepherd_conf
mvn -Pdocker clean install -DskipTests
# --pull and --no-cache pick up the latest base image and Ubuntu security updates
docker-compose build --pull --no-cache web
# Detached, so the databases keep running while you restore files below
docker-compose up -d --build
```

The new volume starts from the image: a newly generated keystore, and connection settings taken from `.env`. If you had customised either, copy just those files back from the backup. Leave `server.xml` and `web.xml` alone, because they are the Tomcat 11 versions.

```console
BACKUP_DIR="$HOME/shepherd-conf-backup"
# Connection settings changed through the setup page:
docker run --rm -v securityshepherd_conf:/conf -v "$BACKUP_DIR":/backup alpine \
  tar xzf /backup/shepherd-conf-backup.tgz -C /conf ./database.properties ./mongo.properties
# Your own TLS certificate: restore the keystore file named by TLS_KEYSTORE_FILE, and make sure
# TLS_KEYSTORE_PASS and ALIAS in .env match it
docker run --rm -v securityshepherd_conf:/conf -v "$BACKUP_DIR":/backup alpine \
  tar xzf /backup/shepherd-conf-backup.tgz -C /conf ./<your keystore file>
docker-compose restart web
```

Delete `$BACKUP_DIR` (or move it somewhere safe) once the upgrade is working. On Linux hosts the archive is owned by root, but you can still delete it because you own the directory.

If you had hand-edited the old `server.xml` or `web.xml` (custom connectors, ports, ciphers and so on), re-apply those edits to the new Tomcat 11 files, using the backup as a reference. Don't copy the old files back.

##### MariaDB 12.3
The database image now runs MariaDB 12.3 (long-term support) instead of 10.6, which is no longer supported. The `data` volume is kept. On its first start, `MARIADB_AUTO_UPGRADE=1` in `docker-compose.yml` upgrades the volume's system tables, after taking a backup of them inside the volume. Back up your data before rebuilding anyway, because a volume can't be moved back to 10.6 once 12.3 has opened it. Run this while the old container is still up. The dump holds every user's password hash, so like the `conf` backup above it goes outside the repository and is readable by you only:

```console
BACKUP_DIR="$HOME/shepherd-db-backup"
mkdir -p "$BACKUP_DIR" && chmod 700 "$BACKUP_DIR"
(umask 077 && docker exec secshep_mariadb sh -c \
  'export MYSQL_PWD="$MYSQL_ROOT_PASSWORD"; exec mysqldump -uroot --all-databases --routines --events' \
  > "$BACKUP_DIR/shepherd-db-backup.sql")
```

Delete `$BACKUP_DIR` (or move it somewhere safe) once the upgrade is working.

# What can Security Shepherd be used for?
Security Shepherd can be used as a;
* Teaching Tool for All Application Security
* Web Application Pen Testing Training Platform
* Mobile Application Pen Testing Training
* Safe Playground to Practise AppSec Techniques
* Platform to demonstrate real Security Risk examples
  
# Why choose Security Shepherd?
There are a lot of purposefully vulnerable applications available in the OWASP Project Inventory, and even more across the internet. Why should you use Security Shepherd? Here are a few reasons;  
* **Wide Topic Coverage**  
Shepherd includes over sixty levels across the entire spectrum of Web and Mobile application security under a single project.
* **Gentle Learning Curve**  
Shepherd is a perfect for users completely new to security with levels increasing in difficulty at a pleasant pace.
* **Layman Write Ups**  
When each security concept is first presented in Shepherd, it is done so in layman terms so that anyone (even beginners) can absorb them.
* **Real World Examples**  
The security risks in Shepherd are real vulnerabilities that have had their exploit impact dampened to protect the application, users, and environment. There are no simulated security risks which require an expected, specific attack vector in order to pass a level. Attack vectors when used on Shepherd are how they would behave in the real world.
* **Scalability**  
Shepherd can be used locally by a single user or easily as a server for a high amount of users.
* **Highly Customisable**  
Shepherd enables admins to set what levels are available to their users and in what way they are presented (Open, CTF and Tournament Layouts)
* **Perfect for Classrooms**  
Shepherd gives it's players user specific solution keys to prevent students from sharing keys, rather than going through the steps required to complete a level.
* **Scoreboard**  
Security Shepherd has a configurable scoreboard to encourage a competitive learning environment. Users that complete levels first, second and third get medals on their scoreboard entry and bonus points to keep things entertaining on the scoreboard.
* **User Management**  
Security Shepherd admins can create users, create admins, suspend, unsuspend, add bonus points, or take penalty points away from users' accounts with the admin user management controls. Admins can also segment their students into specific class groups. Admins can view the progress a class has made to identify struggling participants. An admin can even close public registration and manually create users if they wish for a private experience.
* **Robust Service**  
Shepherd has been used to run online CTFs such as the OWASP Global CTF and OWASP LATAM Tour CTF 2015, both surpassing 200 active users and running with no down time, bar planned maintenance periods.
* **Configurable Feedback**  
An administrator can enable a feedback process, which must be completed by users before a level is marked as complete. This is used both to facilitate project improvements based on feedback submitted and for system administrators to collect "Reports of Understanding" from their students.
* **Granular Logging**  
The logs reported by Security Shepherd are highly detailed and descriptive, but not screen blinding. If a user is misbehaving, you will know.
