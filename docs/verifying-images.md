# Checking the Docker images

The release workflow publishes the Security Shepherd Tomcat image to Docker Hub as [`owasp/security-shepherd`](https://hub.docker.com/r/owasp/security-shepherd). This page shows how to check what's inside an image you pull and where it came from.

## Image tags

| Tag | What it is |
| --- | --- |
| `X.Y.Z`, e.g. `4.0.0` | A release. Doesn't change once published. |
| `X.Y`, `X`, `latest` | The newest release in that line. Moves with each release. |
| `X.Y.Z-SNAPSHOT`, e.g. `4.1.0-SNAPSHOT` | The latest `dev` build of the version in progress. Moves with each push to `dev`. |
| `dev` | The latest `dev` build. Moves with each push to `dev`. |

Snapshot and `dev` images are untested pre-releases. For anything you rely on, use a release tag, or pin the image digest (`owasp/security-shepherd@sha256:…`).

Images from 4.0.0 on (and `dev` and snapshot builds) are multi-platform images for `linux/amd64` and `linux/arm64`. Docker pulls the one that matches your machine, so an Apple Silicon Mac or another ARM host runs the image natively. Each tag points to an image index that lists one image per platform. Add `--platform linux/amd64` or `--platform linux/arm64` to `docker pull` and `docker run` to choose one.

The older images (`3.0`, `3.1`, and `latest` until 4.0.0 is released) are `linux/amd64` only. On an ARM machine, add `--platform linux/amd64` to run them under emulation.

## SBOM

Each published image carries a software bill of materials (SBOM) in [SPDX](https://spdx.dev/) format, generated by BuildKit when the image is built. It lists the operating system packages, Tomcat, and the Java libraries inside the Security Shepherd WAR. Each platform's image has its own SBOM.

Print the SBOM for one platform with Docker Buildx:

```bash
docker buildx imagetools inspect owasp/security-shepherd:4.0.0 --format '{{ json (index .SBOM "linux/amd64").SPDX }}'
```

Use `linux/arm64` for the ARM image, or `--format '{{ json .SBOM }}'` to print both, keyed by platform.

Save it to a file to feed it to other tools, for example to scan it for known vulnerabilities with [Grype](https://github.com/anchore/grype):

```bash
docker buildx imagetools inspect owasp/security-shepherd:4.0.0 --format '{{ json (index .SBOM "linux/amd64").SPDX }}' > shepherd-4.0.0.spdx.json
grype sbom:./shepherd-4.0.0.spdx.json
```

The [Docker Scout](https://docs.docker.com/scout/) CLI reads the same SBOM (it reports "SBOM obtained from attestation"), for your machine's platform unless you add `--platform`. It needs you to be logged in to Docker Hub with any account:

```bash
docker scout sbom owasp/security-shepherd:4.0.0
docker scout cves owasp/security-shepherd:4.0.0
```

Security Shepherd is deliberately vulnerable training software. Scanners report on its dependencies, not on the training lessons and challenges, which are vulnerable by design.

## Build provenance

Each image also carries a [SLSA](https://slsa.dev/) provenance attestation: which source, Dockerfile and build arguments it was built from, and by which GitHub Actions run. As with the SBOM, each platform has its own:

```bash
docker buildx imagetools inspect owasp/security-shepherd:4.0.0 --format '{{ json (index .Provenance "linux/amd64").SLSA }}'
```

This SBOM and provenance are stored next to the image on Docker Hub but aren't signed, so they show how the image says it was built. They don't prove it. For that, check the signed provenance below.

## Signed provenance

The release workflow also signs a SLSA build provenance attestation for every image it pushes, using [GitHub artifact attestations](https://docs.github.com/en/actions/concepts/security/artifact-attestations). It is signed with [Sigstore](https://www.sigstore.dev/), recorded in Sigstore's public transparency log, and stored with GitHub rather than on Docker Hub. Verifying it proves that the image was built from this repository by its release workflow, at the commit and ref it names.

The image is built and signed by a reusable workflow, [`release-build.yml`](../.github/workflows/release-build.yml), that the workflow which starts the build can't change. That meets [SLSA Build Level 3](https://slsa.dev/spec/v1.0/levels#build-l3). Require that workflow as the signer when you verify.

Verify with the [GitHub CLI](https://cli.github.com/). Any GitHub account will do (`gh auth login`):

```bash
gh attestation verify oci://docker.io/owasp/security-shepherd:4.0.0 \
  --repo OWASP/SecurityShepherd \
  --signer-workflow OWASP/SecurityShepherd/.github/workflows/release-build.yml \
  --source-ref refs/tags/4.0.0
```

- `--signer-workflow` rejects attestations made by any other workflow, including other workflows in this repository.
- `--source-ref` checks which ref the image was built from. For a release it's the release tag. For `dev` and snapshot images, use `--source-ref refs/heads/dev`.
- Add `--format json` to see the whole provenance, including the commit and the Actions run that built the image.

`gh` resolves the tag to the image digest and checks the attestation for that digest. For a multi-platform image that is the digest of the image index, which covers every platform: the index lists each platform's image by its own digest. Verify the index digest, not the digest of one platform's image, which has no signed attestation of its own. `docker buildx imagetools inspect owasp/security-shepherd:4.0.0` prints it as `Digest`, and `docker pull` prints the same digest.

To make sure you run exactly what you verified, verify by digest and run by digest:

```bash
gh attestation verify oci://docker.io/owasp/security-shepherd@sha256:<digest> \
  --repo OWASP/SecurityShepherd \
  --signer-workflow OWASP/SecurityShepherd/.github/workflows/release-build.yml
docker run owasp/security-shepherd@sha256:<digest>
```

The older images (`3.0`, `3.1`, and `latest` until 4.0.0 is released) were published before any of this, and have no SBOM, provenance or signature.
